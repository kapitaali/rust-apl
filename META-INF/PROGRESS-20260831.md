### Module 6: Bidirectional Python Communication (Deferred)

**Status:** Shell-out approach works (stateless). Persistent process deferred.

**Blocker:** Thread-local `RefCell<Option<PythonProcess>>` + blocking `read_line` causes test deadlocks in parallel test runner. Three attempts (Mutex, thread-local, timeout-based) all hang when Python produces no output or when tests share the process.

**Decision needed:** Choose one:
1. **Socket-based IPC** — Python process listens on a Unix socket, APL connects per session. Clean separation, no stdin/stdout blocking issues.
2. **pyo3** — Direct Rust↔Python FFI. No process management, true bidirectional. Requires Python dev headers.
3. **Accept shell-out** — Document that ⎕PYTHON is stateless; bidirectional requires external orchestration.

**Recommendation:** Option 3 (shell-out) for now. Revisit with pyo3 when FFI architecture (EXTENSIONS.md) lands.

**Effort:** 2–3 days (if pursuing socket or pyo3).

### Module 5: GTK4 GUI — Architecture

**Status:** Stub registered. Architecture designed below for full implementation.

**Goal:** GTK4 window for interactive APL display — text, tables, plots.

---

#### 1. Architecture Overview

```
┌──────────────────┐         mpsc channel        ┌──────────────────┐
│   APL REPL       │  ─── GtkMessage ──────────▶  │   GTK Thread     │
│   (main thread)  │                              │   (gtk::main)    │
│                  │  ◀── AplResult ───────────  │                  │
│  quad_gtk(B)     │                              │  Window/Widgets  │
└──────────────────┘                              └──────────────────┘
```

GTK4 is **not `Send`** — all GTK operations happen on one dedicated thread. The APL REPL thread sends `GtkMessage` values through an `mpsc::Sender`. GTK receives via `glib::timeout_add_local` polling.

#### 2. Threading Model

- **Main thread (REPL):** Evaluates APL, constructs `GtkMessage`, sends via channel
- **GTK thread:** Runs `gtk::main()`, polls channel every ~100ms, updates widgets
- **No shared state** — all communication via message passing

#### 3. Message Protocol

```rust
enum GtkMessage {
    /// Show a text string in the main display area
    ShowText(String),
    /// Show an image (plot file path)
    ShowPlot(String),
    /// Show tabular data (character matrix)
    ShowTable(Vec<Vec<String>>),
    /// Set a named value (for future two-way binding)
    SetValue { name: String, value: String },
    /// Close the window and quit GTK
    Close,
}
```

#### 4. Widget Structure

```
gtk::Window (title: "⎕GTK — APL Window")
├── gtk::Box (vertical)
│   ├── gtk::Notebook (tabbed content)
│   │   ├── Tab "Text": gtk::Label (scrollable)
│   │   ├── Tab "Plot": gtk::Picture (from file)
│   │   └── Tab "Table": gtk::TreeView or gtk::Label
│   └── gtk::Label (status bar)
```

#### 5. ⎕GTK API Surface

| Command | Behavior |
|---------|----------|
| `⎕GTK 'text' 'hello world'` | Open/update window with text |
| `⎕GTK 'plot' 'plot.png'` | Show image in window |
| `⎕GTK 'table' matrix` | Display character matrix |
| `⎕GTK 'close'` | Close window |
| `⎕GTK.SET 'var' value` | Set a named value |
| `⎕GTK.GET 'var'` | Get a named value (future) |

#### 10. Testing Strategy

- GTK tests require a display server (X11/Wayland). Mark tests `#[ignore]` for CI.
- Use `gtk::init()` guard to prevent double-init in tests.
- Mock the channel receiver for unit tests that don't need a real window.

#### 11. Non-Obvious Notes

- GTK main loop blocks the thread — must use `glib::timeout_add_local` to poll channel
- `gtk::Picture::for_filename()` needs the file to exist at construction time
- GTK widgets are reference-counted (`gtk::Label` is `Clone`) — safe to move into closures
- For headless tests, use `GDK_BACKEND=xvfb` or skip with `#[cfg(feature = "gtk-integration-test")]`
